# 明白金 FinFair 技术与交互设计

> 版本：V1.0
> 对应需求：`docs/prd.md`
> 原则：确定性字段优先使用规则；模型只补充复杂语义；所有模型新增洞察必须通过证据核验。

## 1. 页面结构与信息顺序

1. 首屏：项目定位与教学模拟标识；
2. 双入口：使用教学案例或上传自己的 PDF；
3. 输入区：正式 PDF、宣传文案、分析模式提示和开始核验；
4. 侧栏高级设置：模型厂商、Base URL、模型名、API Key 和保存状态；
5. 结果摘要：字段数、风险数、宣传问题数和证据数；
6. 首要结果：宣传材料与正式说明书逐项对照；
7. 分层标签页：30 秒看懂、风险与最坏情形、Agent 语义增强、购买前问题、结构化结果；
8. 导出区：Markdown、JSON、Word、PDF；
9. 局限与免责声明。

## 2. 分析职责

| 组件 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 规则引擎 | PDF 按页解析、稳定字段抽取、宣传规则检查、基础报告 | 复杂隐含语义和投资判断 |
| 分析 Agent | 基于规则结果和原文提出候选语义洞察 | 直接写入最终可信结论 |
| 核验 Agent | 以第二阶段角色审查候选洞察、证据页码和引文 | 代替程序核实字符串存在性 |
| 程序门控 | 确认引文位于指定页，只接收通过双重核验的洞察 | 判断法律合规性或产品优劣 |
| 展示与导出 | 分层呈现相同分析对象并生成报告 | 修改分析事实 |

处理链路：

```text
PDF/宣传文案
→ 按页文本
→ 规则结果
→（可选）分析 Agent 候选
→ 核验 Agent
→ 程序逐字引用检查
→ 合并结果
→ 页面与多格式报告
```

分析和核验是两个固定逻辑阶段，当前使用同一份厂商、模型与协议配置，各调用一次后停止。它不是两个完全独立的模型，也不包含循环互聊。只有核验状态为支持、且程序能在指定页定位逐字引文的候选才能进入结果。

## 3. 核心数据结构

数据结构定义在 `finfair/core.py`：

- `Evidence`：页码、原文和证据说明；
- `FieldResult`：字段键、名称、值、通俗解释、状态和证据；
- `MarketingFinding`：宣传核验项目、稳定状态、优先级、正式文件通俗结论、说明和证据；
- `AgentInsight`：模型洞察、严重度、说明、页码、引文及核验信息；
- `AgentRunInfo`：模型、协议、阶段完成状态、候选数、核验支持数、门控通过数、拦截数、停止原因和降级错误；
- `AnalysisResult`：字段、风险、问题、宣传发现、Agent 洞察和运行信息的统一结果。

`AnalysisResult` 同时记录文档名、解析页数、提取字符数、空白页数、Agent 接收字符数、截断状态和分析模式，作为页面及报告统一使用的覆盖证据。

API 配置由 `LLMConfig` 表示。页面会话配置不写入 `AnalysisResult`，避免密钥进入导出报告。

## 5. 错误与降级路径

| 情况 | 处理 |
| --- | --- |
| 未提供 PDF | 阻止分析并提示用户 |
| PDF 无可提取文字 | 告知当前不支持纯扫描件 |
| 字段没有可靠证据 | 显示“待确认” |
| 未配置 API | 完整保留规则模式 |
| 模型请求失败或返回非法 JSON | 显示错误，规则结果不丢失 |
| 核验 Agent 拒绝候选 | 不展示为新增语义洞察 |
| 引文不在指定页 | 程序拦截 |
| Word/PDF 导出依赖异常 | Markdown 和 JSON 仍可下载 |

## 6. 文档覆盖与截断

- 规则引擎处理全部已提取页面文字，并记录空白/未提取文字页面；
- 页码从 1 开始保存在证据对象中；
- 模型输入由 `finfair/llm_agent.py` 控制为最多 45,000 个文档字符，长文会被截断；
- 页面与四种报告均显示 Agent 实际接收字符数和截断状态；
- 被截断时明确提示不能将“模型没有发现”解释为“全文不存在”；
- API 失败时保留规则解析页数、字符数和空白页数据，并把模式标为规则降级。

## 7. API Key 与第三方数据边界

- 用户主动开启混合 Agent 后才显示并使用 API 配置；
- Key 保存在 `st.session_state`，不写入 `.env`、仓库、日志或报告；
- 只允许 HTTPS，并拒绝本机和私有网络目标，降低服务端请求伪造风险；
- 文档文字和宣传文案会发送到所选第三方服务商；
- 页面必须在发送前提示数据边界，真实敏感客户资料不得用于课程演示；
- 厂商协议差异由 OpenAI-compatible 或 Anthropic 适配层处理。

## 8. 桌面端和手机端要求

当前交付以桌面端 Demo 为主。基本要求：

- 桌面端在常见浏览器宽度下不出现横向溢出；
- 手机端能够完成阅读、上传、分析和查看核心结论；
- 按钮和提示文字不应被截断；
- 1440px桌面和375px手机视口已完成浏览器复测，页面 `scrollWidth` 与 `innerWidth` 一致；
- 手机上输入区单列排列，摘要指标使用2×2网格；
- 最终证据保存在 `screenshots/rule-mode.png`、`screenshots/mobile.png` 和 `screenshots/marketing-contrast.png`。

动态PDF原文、宣传文案和模型输出使用 `st.write` 等原生安全渲染；`unsafe_allow_html=True` 仅用于静态模板或由程序枚举控制的状态标签。测试用 `<script>` 和事件属性会作为文字处理。

## 9. 报告格式

- Markdown：便于检查和二次编辑；
- JSON：保留结构化结果；
- Word：适合课程材料和人工批注；
- PDF：便于固定版式分享。

四种格式应基于同一个 `AnalysisResult`，宣传核验统一使用 `supported`、`omitted`、`weakened`、`conflicting`、`unclear` 五种机器状态，不得出现核心结论互相矛盾。API Key 不属于报告数据。

## 10. 暂不实现的技术范围

- OCR 和图片海报识别；
- 向量数据库或长期知识库；
- 多用户认证与云端历史记录；
- 多产品批量分析；
- 机构权限、审计后台和私有化部署；
- 自动投资建议、适当性结论或监管认定；
- 未经授权的真实金融客户数据处理。
